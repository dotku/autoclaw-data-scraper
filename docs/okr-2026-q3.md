## 定位

scraper 是 AutoClaw 的**线索生产子系统**，它存在的唯一理由是：**为销售引擎持续产出"高匹配 + 可触达"的潜在客户**，且**产出过程合规、可靠、可审计**。因此季度目标只围绕两件事：**产出质量** 与 **平台可信度**。架构演进（[Part I/II 路线图](./architecture-design.md)）是手段，不是目标本身——下列 KR 把架构 Phase 绑定到可衡量的业务结果。

---

## O1 — 产出"高匹配 + 可触达"的线索（汇入公司 O2）

*解决今天的核心缺口：导入 187 家公司但 0 个可外联联系人。*

| KR | 目标 | 关联 |
|----|------|------|
| KR1.1 | 每月产出 **≥ `TODO(founder)` 家高匹配公司**（经 ICP 打分排序，非全量） | 付费 Apollo 公司搜索 + 打分 |
| KR1.2 | **≥ 70% 的线索带至少 1 个验证过的决策人邮箱** | 付费 Apollo `people/search` + `/people/match` reveal（[架构 §4.2](./architecture-design.md)） |
| KR1.3 | 每条线索带 **ICP 匹配分（fit score）** + 字段完整度，供销售按分跟进 | 新增质量字段（架构 §4.2） |
| KR1.4 | 域名去重准确率 ≥ 99%，curated 层 0 重复/0 空记录 | 现有清洗 + 空结果不覆盖守卫 |

## O3 — 可靠性与可观测（汇入公司 O3；架构 Phase 1–3）

*让定时任务"跑挂了有人知道、单源故障不拖垮整轮"。*

| KR | 目标 | 关联 |
|----|------|------|
| KR3.1 | 每个定时任务接 **结构化日志 + 失败/配额告警（SNS）+ DLQ** | 架构 §7.2 / Phase 3 |
| KR3.2 | 日采集成功率（≥1 segment 产出）**≥ 99%/月**；单轮 < 300s | 架构 §7.3 SLO |
| KR3.3 | `RateLimiter + CreditBudget` 统一额度熔断——**月度 API 额度使用 < 90%**，绝不烧穿 | 架构 §7.1 |
| KR3.4 | 写入前 `zod` schema 校验 + 数量基线告警（疑似源被封自动报警） | 架构 §4.3 / Phase 2 |
| KR3.5 | 两条管线收敛为单一 Lambda 管线；GitHub Actions 退为纯 CI（OIDC，无静态 key） | 架构 §2 / Phase 1 |

## 度量与埋点

- 线索质量指标（`high_fit_leads`、`verified_email_rate`、`fit_score` 分布）随每轮写入 manifest，供周度复盘。
- 可观测指标（CloudWatch EMF）：`leads_collected`、`enrich_calls`、`api_credits_used`、`source_failures`、`run_duration`。

## 节奏与非目标

- **周度**：看 KR 信心灯 + 配额使用率；**月底**：评分、carry/kill。
- **非目标**：实时/流式采集、自建 GPU/LLM、多区域 DR、`tos-risk` 源（除非法务放行）。

## 现实约束

- 早期、资本受限 → 全部 KR **资本轻**：Serverless（~$1–2/mo）、告警/DLQ 按量近零；**付费 Apollo 是唯一刻意支出**（由 O1 的可触达线索价值证明）。
